## 1. Memory Hierarchy & Basics

### 🔧 The Memory Hierarchy
```
Fastest, Smallest, Most Expensive
         ↑
    ┌─────────────┐
    │  Registers  │  ~1 cycle,   ~1 ns,    ~1 KB
    ├─────────────┤
    │    Cache    │  ~4 cycles,  ~4 ns,    ~4 MB
    │  (L1/L2/L3) │
    ├─────────────┤
    │  Main RAM   │  ~100 cycles,~100 ns,  ~16 GB
    ├─────────────┤
    │    SSD      │  ~100K cycles,~0.1 ms, ~512 GB
    ├─────────────┤
    │  Hard Disk  │  ~10M cycles,~10 ms,   ~2 TB
    ├─────────────┤
    │   Tape/     │  seconds,              ~PB
    │   Archive   │
    └─────────────┘
         ↓
Slowest, Largest, Cheapest
```

### 🔧 Key Memory Terms
```
PHYSICAL ADDRESS:  Actual address in RAM hardware (what the memory chip sees)
LOGICAL ADDRESS:   Address generated by CPU / used by program (also called virtual address)
ADDRESS SPACE:     Range of all possible addresses a process can use

MMU (Memory Management Unit):
  Hardware unit that TRANSLATES logical → physical addresses at runtime.
  Every memory access goes through MMU. Transparent to program.

RELOCATION REGISTER (Base Register):
  Simplest MMU: Physical = Logical + Base_Register
  OS sets base register when scheduling each process.

LIMIT REGISTER:
  Max size of process's address space.
  If Logical Address ≥ Limit → trap to OS (segmentation fault!).
```

### 🔧 Memory Protection
```
Hardware checks on every memory access:
  if (logical_address >= limit_register)
      → TRAP to OS → segmentation fault → kill process

This prevents process A from reading/writing process B's memory.
Base + Limit registers are PRIVILEGED → only OS can change them.
Changed on every context switch.
```

## 2. Memory Layout of a Process

### 🔧 Virtual Address Space Layout
```
High Address  0xFFFFFFFF
    ┌──────────────────────┐
    │   Command line args  │  (argc, argv)
    │   Environment vars   │
    ├──────────────────────┤
    │                      │
    │        STACK         │  Local variables, function frames
    │     (grows DOWN ↓)   │  Each function call → pushes frame
    │                      │  return → pops frame
    ├──────────────────────┤
    │          ↕           │  Stack and heap grow toward each other
    │        (gap)         │  Stack overflow = stack hits heap
    ├──────────────────────┤
    │                      │
    │        HEAP          │  malloc(), new, calloc()
    │     (grows UP ↑)     │  Dynamic allocation at runtime
    │                      │
    ├──────────────────────┤
    │    BSS Segment       │  Uninitialized globals → zeroed by OS
    ├──────────────────────┤
    │    Data Segment      │  Initialized globals and static vars
    ├──────────────────────┤
    │    Text Segment      │  Compiled code (read-only)
    │    (Code Segment)    │  Shared between processes running same program
Low Address   0x00000000
```

### 🔧 What Lives Where
```c
int global = 5;           // Data segment (initialized)
int uninit;               // BSS segment (uninitialized, set to 0)
static int s = 10;        // Data segment

int main() {
    int local = 3;        // Stack
    int *p = malloc(100); // p is on stack, 100 bytes allocated on HEAP
    // *p points to heap
    return 0;
}

// Code of main() → Text segment
```

## 3. Contiguous Memory Allocation

### 🧠 Concept
Earliest memory management. Each process occupies a SINGLE contiguous block of memory.
OS maintains a list of free holes and allocated regions.

### 🔧 Memory Allocation Strategies

#### First Fit
```
Scan from BEGINNING of memory.
Allocate the FIRST hole that is big enough.

Memory: [OS 40K][Free 100K][Used 30K][Free 200K][Used 50K][Free 80K]
Request: 70K
First Fit → allocates from first 100K hole (fits 70K, leaves 30K hole)

Pros: Fast (stops scanning early)
Cons: Creates small holes at beginning of memory over time
```

#### Best Fit
```
Scan ALL holes.
Allocate the SMALLEST hole that is big enough.

Same memory, Request: 70K
Best Fit → finds 80K hole (smallest that fits 70K), leaves 10K hole

Pros: Minimizes wasted space in allocated block
Cons: Creates tiny leftover holes, slow (must scan all), tiny holes unusable
```

#### Worst Fit
```
Scan ALL holes.
Allocate the LARGEST hole.

Same memory, Request: 70K
Worst Fit → allocates from 200K hole, leaves 130K hole

Pros: Leaves large holes that future processes can use
Cons: Slow, destroys large holes that big processes need
Simulation studies: First Fit and Best Fit both better than Worst Fit
```

### 📊 Comparison
| Strategy | Speed | External Frag | Best For |
|---|---|---|---|
| First Fit | Fast | Moderate | General use |
| Best Fit | Slow | High (tiny holes) | Minimize waste per allocation |
| Worst Fit | Slow | Worst overall | Rarely used |

## 4. Fragmentation

### 🔧 External Fragmentation
```
Total free memory is enough to satisfy a request,
but it is NOT contiguous — scattered in small pieces.

Example:
  Free: [10K][15K][8K][12K][20K] = 65K total free
  Request: 40K
  No single hole is 40K → REQUEST FAILS despite 65K free!

This is EXTERNAL fragmentation — memory is fragmented OUTSIDE allocated blocks.

Fix: COMPACTION — move all processes to one end, merge free space.
     Expensive (requires relocation) and requires dynamic relocation.
```

### 🔧 Internal Fragmentation
```
Allocated block is LARGER than what was requested.
The wasted space is INSIDE the allocated block.

Example:
  OS allocates memory in units of 8 bytes.
  Process requests 13 bytes → gets 16 bytes.
  3 bytes wasted INSIDE the allocation.

Cause: Fixed-size allocation units (pages, blocks)
Fix: Smaller allocation units (more overhead) or best fit

Average internal fragmentation = page_size / 2
(Last page of each process is half-full on average)
```

### 🔧 Which Allocation Causes Which?
```
Contiguous allocation → EXTERNAL fragmentation (holes between allocations)
Paging               → INTERNAL fragmentation (last page partially used)
Segmentation         → EXTERNAL fragmentation (variable-size segments)
Paged Segmentation   → Only internal (paging eliminates external)
```

## 5. Paging — Complete Deep Dive

### 🧠 The Big Idea
```
Problem: Contiguous allocation → external fragmentation.
Solution: Allow a process's memory to be NON-CONTIGUOUS in physical memory.

Physical memory → divided into fixed-size FRAMES
Process memory  → divided into same-size PAGES
Page Table      → maps each page to the frame it occupies

Process sees: contiguous virtual addresses (logical view)
RAM actually: pages scattered anywhere (physical reality)
MMU handles the translation transparently.
```

### 🔧 Key Definitions
```
PAGE SIZE = FRAME SIZE (always equal, typically 4KB = 2^12 bytes)
PAGE NUMBER (p): which page (upper bits of logical address)
PAGE OFFSET (d): position within the page (lower bits of logical address)
FRAME NUMBER (f): which physical frame

Logical Address  = [  page number  |  offset  ]
                         p                d

Physical Address = [  frame number  |  offset  ]
                          f               d
                   (offset is UNCHANGED in translation)
```

### 🔧 Address Splitting Formula
```
Page size = 2^k bytes  →  offset uses k bits
Logical address space = 2^m bytes  →  logical address uses m bits
                     →  page number uses (m - k) bits
Number of pages = 2^m / 2^k = 2^(m-k)

Physical address space = 2^n bytes  →  physical address uses n bits
                      →  frame number uses (n - k) bits
Number of frames = 2^n / 2^k = 2^(n-k)

Page table has ONE entry per page = 2^(m-k) entries
```

### 🔧 Page Table Structure
```
Page Table:
  Entry 0: frame 5   ← page 0 is in physical frame 5
  Entry 1: frame 2   ← page 1 is in physical frame 2
  Entry 2: frame 8   ← page 2 is in physical frame 8
  ...

Each page table entry (PTE) contains:
  - Frame number (main content)
  - Valid/Invalid bit: 1=page in memory, 0=not in memory (page fault!)
  - Protection bits: R/W/X permissions
  - Dirty bit: 1=page has been modified (must write to disk before evicting)
  - Reference bit: 1=page has been accessed recently (used by replacement algorithms)
  - Present bit: same as valid bit in some architectures
```

### 🔧 Page Table Location
```
Page table stored in MAIN MEMORY (too large for registers).
PTBR (Page Table Base Register): stores address of current process's page table.
Changed on every context switch (privileged operation).

Problem: Every memory access now needs TWO memory accesses:
  1. Access page table (in RAM) to get frame number
  2. Access actual data (in RAM) at physical address
→ Memory access is 2× slower! Solution: TLB (covered in section 7)
```

## 6. Address Translation — Numericals

### 📝 Numerical 1 — Basic Address Translation

**Given:**
- Logical address space: 32 bits
- Page size: 4 KB = 4096 bytes = 2^12 bytes
- Page table (partial): Page 0→Frame 5, Page 1→Frame 3, Page 2→Frame 8, Page 3→Frame 1

**Translate logical addresses: (a) 0x00001A2F  (b) 0x00002008  (c) 0x00003FFF**

**Solution:**
```
Page size = 2^12 → offset = 12 bits (lower 12 bits)
Page number = upper (32-12) = 20 bits

(a) Logical address: 0x00001A2F
    Binary: 0000 0000 0000 0000 0001 | 1010 0010 1111
    Page number = 0x00001 = 1
    Offset      = 0xA2F = 2607

    Page 1 → Frame 3
    Physical address = Frame 3 × 4096 + 2607
                     = 3 × 4096 + 2607
                     = 12288 + 2607
                     = 14895 = 0x00003A2F

    Quick method: Replace page number with frame number:
    0x00001A2F → page=1, frame=3 → 0x00003A2F ✓

(b) Logical address: 0x00002008
    Page number = 0x00002 = 2
    Offset      = 0x008 = 8

    Page 2 → Frame 8
    Physical = 0x00008008 ✓

(c) Logical address: 0x00003FFF
    Page number = 0x00003 = 3
    Offset      = 0xFFF = 4095 (last byte of page)

    Page 3 → Frame 1
    Physical = 0x00001FFF ✓
```

---

### 📝 Numerical 2 — Page Table Size Calculation

**Given:**
- Logical address: 32 bits
- Physical address: 24 bits
- Page size: 2 KB

**Find: (a) Number of pages, (b) Number of frames, (c) Page table size (entries and bytes), (d) Number of bits for frame number in each PTE**

**Solution:**
```
Page size = 2 KB = 2^11 bytes → offset = 11 bits

(a) Number of pages:
    Logical space = 2^32 bytes
    Pages = 2^32 / 2^11 = 2^21 = 2,097,152 pages

(b) Number of frames:
    Physical space = 2^24 bytes
    Frames = 2^24 / 2^11 = 2^13 = 8,192 frames

(c) Page table size:
    Entries = number of pages = 2^21
    Bits per entry for frame number = log2(8192) = 13 bits
    Round up to 2 bytes (16 bits) per entry for alignment
    Page table size = 2^21 × 2 bytes = 4 MB per process!

    → Each process needs 4 MB just for its page table.
    With 100 processes = 400 MB just for page tables. Too large!
    Solution: Multi-level paging (section 8)

(d) Frame number bits = log2(number of frames) = log2(2^13) = 13 bits
```

---

### 📝 Numerical 3 — Physical Address with Offset

**Given:**
- Page size: 512 bytes
- Page table: [6, 4, 3, 7, 0, 1] (index = page number, value = frame number)
- Logical addresses to translate: (a) 0  (b) 515  (c) 2300

**Solution:**
```
Page size = 512 = 2^9 → offset = 9 bits, page number = remaining bits

(a) Logical = 0:
    Page = 0 / 512 = 0, Offset = 0 % 512 = 0
    Frame = page_table[0] = 6
    Physical = 6 × 512 + 0 = 3072

(b) Logical = 515:
    Page = 515 / 512 = 1 (integer division), Offset = 515 % 512 = 3
    Frame = page_table[1] = 4
    Physical = 4 × 512 + 3 = 2048 + 3 = 2051

(c) Logical = 2300:
    Page = 2300 / 512 = 4, Offset = 2300 % 512 = 252
    Frame = page_table[4] = 0
    Physical = 0 × 512 + 252 = 252
```

## 7. TLB & Effective Access Time

### 🧠 The Problem
Page table is in RAM. Every logical→physical translation needs a RAM access.
So every memory instruction needs 2 RAM accesses → program runs 2× slower.

### 🔧 TLB — Translation Lookaside Buffer
```
Small, fast hardware cache (inside MMU/CPU).
Stores recently used page→frame mappings.
~16 to 1024 entries. Access time ~1-5 ns (vs ~100 ns for RAM).

TLB HIT:  page number found in TLB → get frame immediately. Fast!
TLB MISS: page not in TLB → go to page table in RAM → update TLB → retry.

TLB is flushed (cleared) on context switch!
(Otherwise process A's TLB entries would be used for process B)
Modern CPUs use ASID (Address Space ID) to avoid full flush.
```

### 🔧 Address Translation with TLB
```
CPU generates logical address (page p, offset d)
           ↓
    Check TLB for page p
    ┌────────────────┬──────────────────────┐
    │   TLB HIT      │   TLB MISS           │
    │  (found in TLB)│  (not in TLB)        │
    │       ↓        │       ↓              │
    │  frame f       │  access page table   │
    │  immediately   │  in RAM → get frame f│
    │                │  update TLB          │
    └────────┬───────┴──────────┬───────────┘
             ↓                  ↓
    Physical = f × page_size + d
           ↓
    Access physical memory → return data
```

### 🔧 Effective Memory Access Time (EMAT) Formula

```
Let:
  α = TLB hit rate (fraction, e.g., 0.9 for 90%)
  t = TLB access time (time to check TLB)
  m = memory access time (time for one RAM access)

EMAT = α × (t + m) + (1 - α) × (t + 2m)
     = t + m + (1 - α) × m
     = t + (2 - α) × m

Explanation:
  TLB HIT  (probability α):     check TLB (t) + access memory (m) = t + m
  TLB MISS (probability 1-α):   check TLB (t) + access page table (m) + access data (m) = t + 2m

Simplified (ignoring TLB access time, just counting memory accesses):
  EMAT = α × (1 memory) + (1-α) × (2 memories) = (2 - α) × m
```

### 📝 Numerical 1 — EMAT Calculation

**Given:**
- TLB access time: 20 ns
- Memory access time: 100 ns
- TLB hit rate: 80%

**Find EMAT.**

```
EMAT = α × (t + m) + (1 - α) × (t + 2m)
     = 0.8 × (20 + 100) + 0.2 × (20 + 200)
     = 0.8 × 120 + 0.2 × 220
     = 96 + 44
     = 140 ns

Without TLB: every access = t + 2m = 20 + 200 = 220 ns
With TLB: 140 ns
Speedup = 220/140 = 1.57× faster
```

---

### 📝 Numerical 2 — Find Hit Rate Given EMAT

**Given:**
- TLB time: 10 ns, Memory time: 200 ns
- Required EMAT: 140 ns

**Find minimum TLB hit rate.**

```
EMAT = α(t + m) + (1-α)(t + 2m)
140  = α(10+200) + (1-α)(10+400)
140  = 210α + 410(1-α)
140  = 210α + 410 - 410α
140  = 410 - 200α
200α = 410 - 140 = 270
α    = 270/200 = 1.35

That's > 1, impossible. Let me re-check...
With t=10, m=200: minimum EMAT (α=1) = 10+200 = 210 ns.
So 140 ns is impossible with these values.

Revised: m = 100 ns:
140  = α(10+100) + (1-α)(10+200)
140  = 110α + 210(1-α)
140  = 110α + 210 - 210α
140  = 210 - 100α
100α = 70
α    = 0.70 = 70% hit rate needed ✓
```

---

### 📝 Numerical 3 — EMAT with Two-Level Memory (Cache + RAM)

**Given:**
- TLB access: 5 ns, hit rate: 90%
- Cache access: 10 ns, hit rate: 95%
- RAM access: 100 ns

**Find EMAT for data access (assume page always in memory).**

```
First: resolve TLB (page table translation):
  TLB portion = 0.9 × 5 + 0.1 × (5 + 100) = 4.5 + 10.5 = 15 ns
  (Miss: check TLB + go to RAM for page table)

Then: access data (cache hierarchy):
  Data portion = 0.95 × 10 + 0.05 × (10 + 100) = 9.5 + 5.5 = 15 ns

Total EMAT = TLB portion + Data portion = 15 + 15 = 30 ns
```

## 8. Multilevel Paging

### 🧠 The Problem with Single-Level Page Tables
```
32-bit address space, 4KB pages:
  Page table entries = 2^32 / 2^12 = 2^20 = 1,048,576 entries
  At 4 bytes per entry = 4 MB per process

64-bit address space, 4KB pages:
  Entries = 2^64 / 2^12 = 2^52 entries → 16 petabytes per process!
  Absurd. Even 32-bit is wasteful.

Key insight: Most of a process's 4GB virtual space is UNUSED.
Why maintain page table entries for unmapped pages?
Solution: Only allocate page table for parts actually used.
```

### 🔧 Two-Level Paging
```
Logical address split into THREE parts:
  [ p1 | p2 | offset ]
   ↑      ↑      ↑
Outer   Inner   Offset
page    page    within
table   table   page
index   index

p1 → index into OUTER page table (always in memory, small)
     Outer page table entry → address of INNER page table
     (Inner table only allocated if that region is used)
p2 → index into INNER page table
     Inner page table entry → frame number
offset → unchanged

Memory accesses with 2-level paging and NO TLB: 3 accesses
  (outer table + inner table + data)
With TLB hit: still just 1 + 1 = 2 (TLB + data)
```

### 📝 Numerical — Two-Level Page Table

**Given:**
- Logical address: 32 bits
- Page size: 4 KB (2^12)
- Page table entry: 4 bytes
- Outer page table uses 10 bits, Inner uses 10 bits, Offset 12 bits

**Find: Size of outer page table, max size of one inner page table, total page table overhead for a process using only 12 MB of memory.**

```
Outer page table:
  p1 = 10 bits → 2^10 = 1024 entries × 4 bytes = 4 KB

One inner page table:
  p2 = 10 bits → 2^10 = 1024 entries × 4 bytes = 4 KB

For 12 MB process:
  Pages needed = 12 MB / 4 KB = 3072 pages
  Inner tables needed = ceil(3072 / 1024) = 3 inner tables
  Inner table space = 3 × 4 KB = 12 KB
  Outer table space = 4 KB (always fully allocated)
  Total overhead = 4 + 12 = 16 KB

Compare with single-level:
  Single-level = 1024 × 1024 × 4 bytes / 1024 = 4 MB overhead
  Two-level = 16 KB → massive saving! ✓
```

### 🔧 Three-Level Paging (64-bit systems)
```
64-bit: [p1(9) | p2(9) | p3(9) | p4(9) | offset(12)]
This is x86-64 four-level paging (PML4)!
4 memory accesses without TLB (PML4 → PDPT → PD → PT → data)
With TLB hit: just 1 access
```

## 9. Segmentation

### 🧠 Concept
```
Paging is the OS view (convenient, fixed-size).
Segmentation is the USER/PROGRAMMER view (logical units of varying size).

A program has:
  - Code segment
  - Data segment
  - Stack segment
  - Heap segment
  - Library segments

Each segment can grow/shrink independently.
Programmer sees: segment_number + offset (not just a flat address).
```

### 🔧 Segment Table
```
Each entry has:
  BASE:  starting physical address of segment
  LIMIT: length of segment

Translation:
  Logical address = (segment_number s, offset d)
  Check: if d >= LIMIT[s] → trap (segmentation fault!)
  Physical = BASE[s] + d

Segment table stored in memory, indexed by segment number.
STBR (Segment Table Base Register) points to segment table.
```

### 🔧 Paging vs Segmentation Summary

| Property | Paging | Segmentation |
|---|---|---|
| **Division** | Fixed-size pages | Variable-size segments |
| **External fragmentation** | ❌ None | ✅ Yes |
| **Internal fragmentation** | ✅ Yes (last page) | ❌ None |
| **User visibility** | Transparent | User-defined |
| **Address** | Single linear space | (segment, offset) pair |
| **Protection** | Uniform per page | Per-segment (R/W/X) |
| **Sharing** | Page-level sharing | Easy segment sharing |

### 🔧 Paged Segmentation
```
Combine both: segments divided into pages.
Eliminates external fragmentation (paging) while preserving logical structure (segments).
Used in: Intel x86 (historically), Multics

Address: segment → page table for that segment → frame → offset
Two page table lookups → slower, but TLB helps
```

## 10. Virtual Memory & Demand Paging

### 🧠 The Core Insight
```
Programs DON'T need all their code/data in RAM simultaneously.
You never run ALL paths of a program in one execution.
A 1 GB program might use only 50 MB during typical run.

Virtual Memory: Allow process to use more memory than physically available.
Keep only NEEDED pages in RAM. Rest on disk (swap space).
Load pages ON DEMAND when accessed.
```

### 🔧 Demand Paging
```
At process start: load NOTHING (or just first page).
When program accesses a page not in memory → PAGE FAULT.
OS handles page fault: loads the page from disk.
Program continues as if nothing happened (transparent).

Valid-Invalid bit in page table:
  1 (valid):   page is in physical memory
  0 (invalid): page is NOT in memory (on disk or never allocated)
               → accessing this page causes PAGE FAULT
```

### 🔧 Page Fault Handling — Step by Step
```
1. CPU accesses virtual address
2. MMU checks page table → valid bit = 0
3. MMU raises PAGE FAULT exception → trap to OS
4. OS checks: is this address LEGAL?
   NO  → segmentation fault, kill process
   YES → page is on disk, bring it in
5. OS finds a free frame
   No free frame? → run PAGE REPLACEMENT algorithm
6. OS reads page from disk into free frame (slow! ~10ms)
7. OS updates page table: frame number + valid bit = 1
8. OS restarts the faulting instruction (not next instruction!)
9. Process continues normally, unaware of the page fault

Page fault cost ≈ 10 ms (disk seek + rotational latency + transfer)
Normal memory access ≈ 100 ns
Page fault is 100,000× slower than normal access!
```

### 🔧 Effective Access Time with Page Faults

```
Let:
  p = page fault rate (probability of page fault, 0 ≤ p ≤ 1)
  m = memory access time (e.g., 100 ns)
  page_fault_time = time to handle page fault (e.g., 10 ms = 10,000,000 ns)

EMAT = (1-p) × m + p × page_fault_time

For EMAT to be < 10% degradation:
  We want EMAT < 1.1 × m = 110 ns
  (1-p) × 100 + p × 10,000,000 < 110
  100 - 100p + 10,000,000p < 110
  9,999,900p < 10
  p < 10 / 9,999,900 ≈ 0.000001 = 1 in 1,000,000

Page fault rate must be < 1 per million accesses for good performance!
```

### 📝 Numerical — EMAT with Page Faults

**Given:**
- Memory access time: 200 ns
- Page fault service time: 8 ms = 8,000,000 ns
- Page fault rate: 1 per 1000 accesses (p = 0.001)

**Find EMAT.**

```
EMAT = (1 - p) × m + p × page_fault_time
     = (1 - 0.001) × 200 + 0.001 × 8,000,000
     = 0.999 × 200 + 8,000
     = 199.8 + 8,000
     = 8,199.8 ns ≈ 8.2 μs

Without page faults: 200 ns
With p=0.001: 8,200 ns → 41× slower!

This shows why minimizing page faults is CRITICAL.
```

## 11. Page Replacement Algorithms — Full Numericals

### 🧠 Setup
```
When a page fault occurs and NO free frames exist:
OS must EVICT a page from memory to make room.
Which page to evict? → Page Replacement Algorithm.

Goal: Minimize page faults (minimize disk accesses).
Reference string: sequence of page numbers accessed by process.
```

### 11.1 FIFO — First In First Out

```
Replace the page that has been in memory the LONGEST.
Maintain a queue of pages in order of arrival.

Simple. Easy to implement.
Does NOT approximate optimal.
Suffers from BELADY'S ANOMALY.
```

### 📝 FIFO Numerical — 3 Frames

**Reference string: 7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2**
**Frames: 3**

```
Pages in memory | Fault?
─────────────────────────────────────────────────────────
7     | [7, -, -]          | ✗ FAULT (cold start)
0     | [7, 0, -]          | ✗ FAULT
1     | [7, 0, 1]          | ✗ FAULT
2     | [2, 0, 1] (evict 7)| ✗ FAULT  ← 7 was oldest
0     | [2, 0, 1]          | ✓ HIT
3     | [2, 3, 1] (evict 0)| ✗ FAULT  ← 0 was oldest
0     | [2, 3, 0] (evict 1)| ✗ FAULT  ← 1 was oldest
4     | [4, 3, 0] (evict 2)| ✗ FAULT  ← 2 was oldest
2     | [4, 2, 0] (evict 3)| ✗ FAULT  ← 3 was oldest
3     | [4, 2, 3] (evict 0)| ✗ FAULT  ← 0 was oldest
0     | [0, 2, 3] (evict 4)| ✗ FAULT  ← 4 was oldest
```

### 📝 Belady's Anomaly — FIFO with 4 Frames

**Same string: 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5**

```
With 3 frames: 9 page faults
With 4 frames: 10 page faults  ← MORE faults with MORE frames!

This is BELADY'S ANOMALY — unique to FIFO.
More memory can cause more page faults.
LRU and OPT do NOT suffer from Belady's anomaly.
```

### 11.2 OPT — Optimal Page Replacement

```
Replace the page that will NOT be used for the LONGEST TIME in the future.
Requires knowing future → IMPOSSIBLE to implement in practice.
Used as BENCHMARK to compare other algorithms.
Always gives minimum possible page faults.
```

### 11.3 LRU — Least Recently Used

```
Replace the page that was LEAST RECENTLY USED (used longest ago).
Uses PAST behavior to approximate future (locality of reference).
Near-optimal performance in practice.
No Belady's anomaly.

Implementation:
  Counter: each page has timestamp of last use. Evict smallest timestamp.
  Stack: maintain stack of page numbers. Most recently used on top.
         On access: move page to top. Evict from bottom.
```

### 11.4 LRU Approximations

```
True LRU is expensive (hardware counter or sorted list per access).
OS uses approximations:

REFERENCE BIT (Clock Algorithm / Second Chance):
  Each frame has a reference bit, set to 1 when accessed.
  OS periodically clears all reference bits.
  
  On page fault → scan frames in circular order (clock hand):
    Bit=1: clear to 0, advance hand (second chance)
    Bit=0: EVICT this page (hasn't been used since last scan)

ENHANCED CLOCK (Reference + Dirty bits):
  (0,0) → not referenced, not dirty → BEST to evict
  (0,1) → not referenced, dirty → must write to disk (more expensive)
  (1,0) → referenced, not dirty → likely to be used again
  (1,1) → referenced, dirty → worst to evict
  Evict in order: (0,0) → (0,1) → (1,0) → (1,1)
```

## 12. Thrashing & Working Set Model

### 🧠 Thrashing
```
THRASHING: Process spends more time paging than executing.
CPU utilization DROPS because processes are always waiting for pages.

Cause:
  OS sees low CPU utilization → adds MORE processes (to improve utilization)
  More processes → each gets fewer frames
  Fewer frames → more page faults
  More page faults → more I/O wait → even less CPU utilization
  Vicious cycle → system grinds to a halt

Graph:
  CPU Utilization
       |      *
       |    *   *
       |  *       *
       | *          * ← THRASHING begins here
       |*
       └──────────────── Degree of Multiprogramming
```

### 🔧 Working Set Model
```
LOCALITY OF REFERENCE: Programs tend to access the same set of pages
repeatedly for a period of time, then move to a new set.

WORKING SET W(Δ): Set of pages accessed in the last Δ references.
Δ = working set window (parameter).

Principle: Give each process enough frames for its working set.
  If not enough total frames → REDUCE multiprogramming (swap out a process).
  Never allocate frames below working set size.

Total demand D = Σ |W(Δ)| for all processes
If D > total frames → thrashing possible → swap out a process
```

### 🔧 Page Fault Frequency (PFF) Strategy
```
Alternative to working set:
  Set UPPER and LOWER bounds on acceptable page fault rate.

  If fault rate > UPPER bound → process needs more frames → GIVE it frames
  If fault rate < LOWER bound → process has too many frames → TAKE some back
  If fault rate > UPPER and no free frames → SWAP OUT a process

More reactive than working set (responds to actual fault rate).
```

## 13. MCQ Traps & Exam Q&A

### ⚠️ THE TRAPS

---

**TRAP 1: "Paging eliminates ALL fragmentation"**
❌ WRONG. Paging eliminates EXTERNAL fragmentation.
But paging introduces INTERNAL fragmentation (last page is partially full).
Average internal fragmentation = page_size / 2 per process.

---

**TRAP 2: "More frames always reduces page faults"**
❌ Almost always true, BUT not for FIFO — Belady's Anomaly!
For LRU and OPT: more frames = same or fewer faults (monotone stack property).
For FIFO: more frames CAN increase page faults (Belady's).

---

**TRAP 3: "TLB miss means page fault"**
❌ COMPLETELY WRONG. These are separate things.
TLB miss: page IS in memory but mapping not cached in TLB → go to page table in RAM.
Page fault: page is NOT in memory → must load from disk.
TLB miss → page table lookup → fast (RAM access).
Page fault → disk access → very slow.
TLB miss does NOT equal page fault!

---

**TRAP 4: "Page size and frame size can be different"**
❌ WRONG. Page size ALWAYS equals frame size. They're the same unit.
Page = view from process's perspective.
Frame = view from physical memory's perspective.
Same size. This is fundamental to how paging works.

---

**TRAP 5: "On page fault, OS restarts the NEXT instruction"**
❌ WRONG. OS restarts the SAME (faulting) instruction.
Process needs to re-execute the instruction that caused the fault,
now that the page is in memory.
Re-executing next instruction would skip the operation that caused the fault.

---

**TRAP 6: "Logical address = Physical address in paging"**
❌ WRONG. That's only true in very simple systems (single process, no relocation).
In paging, logical (virtual) address ≠ physical address.
MMU translates every time.
Page number changes; offset stays the same.

---

**TRAP 7: "Thrashing is caused by too little RAM"**
⚠️ PARTIAL. Thrashing is caused by too many processes competing for RAM.
Fix is NOT always to add RAM — reducing multiprogramming also fixes it.
Working set model addresses root cause: ensure each process has its working set.

---

**TRAP 8: "Dirty bit is set when page is loaded from disk"**
❌ WRONG. Dirty bit is set when page is WRITTEN TO (modified) in memory.
On load: dirty bit = 0 (clean).
After write: dirty bit = 1 (modified, must write back to disk before evicting).
If dirty bit = 0: can just overwrite the frame without writing to disk.

---

**TRAP 9: "Two-level paging is always slower than single-level"**
✅ TRUE without TLB (more memory accesses).
But FALSE in practice — TLB hides the extra level.
With TLB hit: both single and multi-level need only 1 memory access (TLB + data).
Two-level is used because it saves page table MEMORY, not because it's faster.

---

**TRAP 10: "Segmentation fault = page fault"**
❌ WRONG. Different errors.
Segmentation fault: accessing memory OUTSIDE legal address space (invalid address).
Page fault: accessing valid address whose page is currently NOT in RAM (valid, just swapped out).
Seg fault → typically kills process.
Page fault → OS loads page, process continues normally.

### 📋 Master Formula Sheet

```
ADDRESS TRANSLATION:
  Page number  p = logical_address / page_size
  Offset       d = logical_address % page_size
  Physical address = frame_number × page_size + d

  Bits for offset    = log₂(page_size)
  Bits for page num  = logical_address_bits - offset_bits
  Number of pages    = 2^(page_number_bits)
  Number of frames   = 2^(frame_number_bits)

PAGE TABLE:
  Entries = virtual_address_space / page_size
  Size    = entries × bytes_per_entry
  Internal fragmentation (avg per process) = page_size / 2

EMAT FORMULAS:
  With TLB:
    EMAT = α(t + m) + (1-α)(t + 2m)
         = t + m(2 - α)
    where α=hit rate, t=TLB time, m=memory time

  With page faults:
    EMAT = (1-p) × m + p × page_fault_time
    where p=page fault rate, m=memory time

  With both TLB and page faults (combined):
    EMAT = α × m + (1-α) × 2m + p × page_fault_service
    (approximate, ignoring TLB access time itself)

WORKING SET:
  If Σ|W(Δ)| > total_frames → thrashing risk → swap out a process

PAGE FAULT RATE FOR <10% DEGRADATION:
  p < (0.1 × m) / (page_fault_time - m) ≈ m / page_fault_time × 0.1
```
